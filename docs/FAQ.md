# 故障 FAQ：按现象排查

本文面向第11批本地候选；公开v0.2.8不包含全部后续能力。先核对`qingnode version`、候选提交和[当前支持矩阵](CAPABILITIES.md)。完整短流程见[安装到验收](GETTING_STARTED.md)，本轮结果与未测项见[BATCH11.md](BATCH11.md)。


先找下面最接近的现象，按“可确定检查 → 可能原因 → 安全操作”处理。这里的检查结果只覆盖它实际检查的范围；“服务运行中”“配置通过”“本机正在监听”都不能直接证明公网客户端能连接。

> 下文保留原发行版已适用的基础排错路径，当前State9、端点、证书和附属服务按本候选文档核对。旧服务器需明确升级后才获得新能力；历史结果仍见[测试报告](TEST_REPORT.md)，不能转记为本轮成功。

## 先收集什么信息

在自己的 VPS 终端运行：

```bash
sudo qingnode version
sudo qingnode overview
sudo qingnode status
sudo qingnode list
sudo qingnode ports
sudo qingnode firewall status
sudo qingnode logs
```

这些入口分别查看版本、本机总览、服务、节点、监听、防火墙检测和脱敏日志。需要联网排查 DNS、证书、REALITY 目标等时，再运行：

```bash
sudo qingnode diagnose
```

`diagnose` 与 `doctor` 相同；会联网，完成后保存首页诊断历史，不修改节点参数或自动重启服务。首页 `overview` 只读本机，不会联网检查更新或替你登记公网成功。本次查询改进中，`list`、`info`、`export`、`render`、`core check`、`firewall status` 也不会自动恢复中断事务。发现事务未完成时先保留现场，按后面的恢复流程处理。

反馈时记录系统版本、CPU 架构、QingNode/核心版本、失败步骤、具体错误、客户端版本与所用协议。发送前检查日志、截图和文件，删去密码、私钥、完整链接、二维码及订阅凭据；不要公开 `state.json`、服务器配置或卸载快照。

## 服务运行中，但客户端连接失败

**可确定检查**：用 `status` 确认本项目服务是否运行；用 `ports` 查看对应 TCP/UDP 是否监听；用 `list` 和 `info --id 节点ID`核对启用状态、地址、端口、协议及凭据。`diagnose` 可以检查本机配置、证书和目标条件。它们都无法单独证明云安全组、NAT 映射、设备网络或客户端认证已经正确。

**可能原因**：客户端还在用旧链接、导入了其他设备凭据、服务器地址错误、监听地址不覆盖所需 IP 家族、云安全组/本机防火墙未放行、NAT 外部端口不同、客户端内核不支持协议、TLS 或认证参数不匹配。这里只列可能性，不能凭服务为绿色就确定是哪一项。

**安全操作**：重新导出所选节点和凭据，与客户端中的连接参数逐项比较；核对安全组、映射和本机规则，再从客户端实际连接。不要清空防火墙、关闭证书校验、修改 SSH 或轮换密钥来试错。二维码/URI 导入成功也只是导入成功，还需 HTTPS 和适用的 UDP 实测。

## 安装报下载超时、DNS 错误、HTTP 404 或校验失败

**可确定检查**：看失败阶段和 `/var/log/qingnode-install-XXXXXXXX.log` 中的错误摘要，核对安装脚本指定的仓库/版本、CPU 架构和官方发行资产是否存在。日志权限为 600，请在自己的终端查看并在分享前脱敏。

**可能原因**：DNS 或出站 HTTPS 受限、GitHub API 限额、软件源不可达、指定版本/资产未发布、下载中断、本地包不完整或摘要不匹配。HTTP 404 不能单独证明 DNS 坏了；摘要失败也不能当作“下载慢”忽略。

**安全操作**：使用 [README 的完整下载入口](../README.md#快速安装)重试，或使用已经校验的完整本地发行包与本架构官方核心归档。缺 curl/wget 时按[平台说明](PLATFORMS.md)使用对应的 apt、dnf 或 apk 安装其中一种。不要改用未知镜像、`curl -k`、`wget --no-check-certificate` 或删除校验步骤。安装器发现本地包损坏会停止，不会悄悄切在线下载。

历史 v0.2.1 的 `VERSION` 字段冲突和 v0.2.2 的受管目录权限问题已有后续修复。遇到相同文字先核对实际版本与日志，再按 [旧版本恢复说明](../README.md#旧版本安装失败时的恢复)使用既有修复入口；不要把所有新故障都归到历史原因。

## 提示端口被占用，或改端口后连不上

**可确定检查**：运行 `sudo qingnode ports`，核对具体监听地址、端口、TCP/UDP 和进程。REALITY 使用 TCP，Hysteria2 使用 UDP，SS2022 同时使用两者；同一数字端口是否冲突取决于实际监听范围及传输协议。

**可能原因**：已有网站、SSH、其他代理或另一节点占用了端口；通配 IPv4/IPv6 监听与指定地址重叠；客户端、云安全组或映射仍指向旧端口。服务商的外部端口未映射也不会在本机占用列表中体现。

**安全操作**：选择一个自己的网络允许且未占用的端口，或使用提示提供的自动/随机选项。不要结束不认识的进程，也不要停掉其他 sing-box 实例。修改成功后重新导出，并同步安全组、NAT 和手动防火墙；已经启用本项目 UFW 规则管理时才会同步相应项目规则。

## Hysteria2 证书、域名或 ACME 失败

**可确定检查**：先读错误是证书名称不匹配、证书过期/未生效、证书私钥不匹配，还是自动签发失败。核对客户端 SNI、证书域名、系统时间和证书完整链。HTTP-01另需正确的公网DNS和TCP 80映射；DNS-01检查受支持提供者的API权限、委派和传播，不要求公网80。节点的UDP端口要另行放行。

**可能原因**：A/AAAA 指向错误地址、TCP 80 被网站占用、CA 限额或签发等待时间、设备不信任签发链、导入的证书已过期、原证书文件续期后未重新导入。ACME 在首页显示“期限未知”只是程序没有核验实际签发期限，不能据此认定证书有效或无效。

**安全操作**：按[证书生命周期说明](CERTIFICATES.md)修正DNS、域名或证书。已有网站占TCP 80时可用有效PEM，或明确配置受支持的DNS-01资源；不要让排查脚本停止网站。PEM续期后通过证书管理入口导入新证书，或使用已有的 `edit --cert ... --key ...` 参数。私有CA/自签名需要另外确认客户端信任设置，不能假定标准导出自动完成信任配置。

## REALITY 目标探测失败

**可确定检查**：核对 SNI、握手目标 `主机:端口`、VPS 的 DNS/出站连接及系统时间。可运行 `sudo qingnode reality-targets` 查看当前探测结果；这个入口联网，但不修改已有节点。

**可能原因**：目标不满足 TLS 1.3/HTTP2、被项目目标排除策略拒绝、DNS/地址变化、VPS 当前连不到该目标或网络超时。测速结果反映 VPS 到目标的建连耗时，不能当作手机到节点的延迟和下载速度。

**安全操作**：使用实际通过检查的目标，手动更换 SNI/握手目标时重新导出到客户端。不要关闭目标检查或把旧节点 UUID、密钥和 short ID 全部重建；地址或目标问题不证明身份已经损坏。

## SS2022 导入后认证失败

**可确定检查**：客户端加密方式必须为 `2022-blake3-aes-256-gcm`，密码格式包含服务密钥与所选用户密钥，两部分之间有 `:`。使用 `export --id 节点ID --user 凭据ID --format uri` 重新取得完整链接，核对节点/凭据选择；不要把密码或密钥贴到反馈中。

**可能原因**：客户端只支持传统 Shadowsocks、内核不支持该多用户格式、手工复制遗漏部分密码、使用轮换前链接、选择了别的设备凭据。URI 可生成不代表所有应用都支持这些参数。

**安全操作**：核对客户端内核说明并完整重新导入。TCP 和 UDP 两种流量都要核对。若明确需要轮换，先看执行前影响范围：单个用户凭据轮换影响该用户，服务密钥轮换会使该节点全部旧客户端失效。

## IPv6 或 NAT VPS 特别容易连不上

**可确定检查**：确认客户端网络有 IPv6、域名 AAAA 正确、服务监听覆盖 IPv6、防火墙及安全组允许 IPv6。NAT VPS 要查服务商给出的公网地址、外部端口、本机映射端口及 TCP/UDP；出站公网 IP 探测不能证明入站映射。

**可能原因**：设备只有 IPv4、域名优先走不可达的 AAAA、域名节点只监听 IPv4、外部端口不等于本机端口、NAT 只映射 TCP 而没有 UDP。当前已用Host/ConnectPort保存客户端端点，Listen/Port保存本地绑定；URI和客户端使用外部连接端口，端口检查和防火墙使用本地监听。

**安全操作**：IPv4 可用时使用已确认可达的 IPv4 路径；按 [端点与双栈说明](ENDPOINTS.md)配置监听和映射。内外端口不同的 NAT，客户端连接端口应填外部端口，服务器保留实际本机监听端口。不要把改变节点端口当作自动修复上游映射。

## 找不到节点、凭据，或二维码/导出文件有问题

**可确定检查**：先 `sudo qingnode list`，再使用自己的 ID 或名称。README 的 `main` 只是示例；节点改名后 ID 仍保持。多个凭据必须选定一个；`--user` 接受凭据 ID 或名称。导出文件已存在时会拒绝覆盖，这是保护行为。

**可能原因**：原样使用示例名称、节点已改名/停用/删除、没有选设备凭据、终端太窄、把文件路径或 Base64 文本当在线订阅网址、导入了 provider 片段而非完整配置。

**安全操作**：复制列表中真实 ID，选择正确凭据，导出到新文件名；二维码错位改用 URI。把 JSON/YAML 安全下载到设备，从本地配置入口导入。导出不会带 REALITY 服务端私钥，但含客户端认证信息；不要上传公开粘贴站或在线二维码工具。

## 菜单输错、想返回，或提示“需要交互终端”

**可确定检查**：确认是否在正常 SSH 终端运行 `sudo qingnode`，以及当前步骤提示的返回方式。自动化/管道输入不应依赖交互菜单，使用具体 CLI 命令及 `--help`。

**本次菜单改进**：节点和凭据选择输入 `0` 正常返回；无效序号重问当前项；输入结束时安全退出。创建向导提示支持 `:cancel`，取消未提交的节点/凭据；导出格式输入 `0` 返回，回车默认 URI，仍支持原格式文字。这些本次改动不表示旧发行包已经具有相同行为。

**安全操作**：看到对应提示后使用其取消方式。创建向导取消不会撤销外层安装器已完成的依赖安装、文件下载或目录准备。操作已经进入配置应用、升级或恢复时，中断属于另一类问题，按下面的事务恢复流程处理。不要把 `0` 作为端口或密码等所有输入项的通用取消值。

## 恢复中断事务、回退配置，还是恢复备份

这三项用途不同，请先看失败发生在哪一步。它们可能改变配置和服务，不能当普通查询命令使用。

v0.2.8 的 `backup` 不再自动恢复事务。它在同一管理锁内检查事务/卸载记录，存在记录或无法确认时拒绝生成不确定的快照，提示先 doctor 再决定 recover；正常备份仍写加密输出和观测历史。遇到中断先保留当前目录、事务记录和日志，不把配置备份当作完整故障现场归档。旧版本仍可能自动恢复，应先核对版本。

| 情况 | 先确认的内容 | 适合的操作及影响 |
| --- | --- | --- |
| 更新/修改中断，提示事务未完成 | `doctor`、日志及现有数据；保留当前目录与恢复记录 | `recover` 按持久记录收尾或恢复，可能恢复旧配置/核心/服务状态 |
| 一次已完成的变更造成问题 | 确认没有待恢复事务后先备份；确认上一配置代确实是希望恢复的版本 | `rollback` 回到上一配置代及其核心版本，可能恢复旧地址、端口或凭据 |
| 当前数据损坏或要从已有备份恢复 | 备份文件、正确口令、核心版本及跨机器网络参数 | `restore` 用备份中的节点状态替换当前状态；恢复前会加密备份当前配置 |

**安全操作**：先查看和保管数据，再选择一项对应操作。中断事务明确需要恢复时运行 `sudo qingnode recover`。确认要回退上一代后运行 `sudo qingnode rollback`。确认要用备份替换现有节点后，把文件路径换成自己的真实备份，再运行 `sudo qingnode restore --file /root/backup.qnbak --yes`；`--yes` 是明确接受替换的参数，不要盲目照抄。

加密备份口令至少 12 字节，不回显；忘记口令无法找回。非交互恢复使用权限 600 的 `--password-file`。恢复前备份使用本次恢复口令。普通QNBK2配置备份不包含ACME运行存储；QNBK3完整迁移另纳入受管证书、私钥、ACME账户/存储及订阅权限，必须满足一致性停止证明。外部引用、独立monitor资料或附属部署缺项时明确受限，不能漏项称完整。核心程序、全机防火墙和宿主调优不随包覆盖；跨机器恢复重新核对核心、init/账户/路径、外部端点，必要时使用`--manual-firewall`。详见[迁移说明](MIGRATION.md)。

数据库严重损坏、未知 schema 或历史核心缺失时，管理器会停止，不能承诺 `recover` 必然修好。不要删除事务记录、状态目录或历史代，也不要手工修改 state.json 来猜测身份。卸载前明文快照虽然权限为 600，仍含秘密；恢复方法见 [README 的卸载说明](../README.md#卸载)。

## 更新失败、显示尚未适配，或想重新安装

**可确定检查**：确认更新对象是 sing-box 核心还是 QingNode 管理器；看失败阶段是下载、摘要、候选配置检查还是服务激活。`core versions` 或菜单检查更新会联网查询，不能代替兼容测试；最新上游版本可能尚未适配。

**可能原因**：归档/架构不匹配、官方摘要不可得、版本超过允许范围、候选配置不兼容、服务启动或权限问题。配置更新失败后已经回退，意味着保住了旧配置，并不代表新版本可用。

**安全操作**：保留旧核心、历史代和节点，按日志处理失败阶段。需要重新安装管理器时使用 [README 的重装入口](../README.md#下载和重复安装)，重复安装保留既有参数和凭据；不要删除数据求“干净重装”。涉及中断记录时先按上述恢复流程处理。新导出、新版本或恢复后都要再次在自己的客户端实测。

更多命令、许可与验证范围见 [README](../README.md)；新手首次操作见 [安装到导入指南](GETTING_STARTED.md)。

## 控制器不可用、未知状态与下一步

```bash
qingnode capabilities --skip-loopback --json
```

实际PID1、控制器可用性和命令存在分别报告。普通容器里有systemctl/rc-service，不等于它们正在管理服务。缺TUN不阻挡普通节点；缺少权限时不假报成功，也不把代理常驻root。完整服务定义、systemd drop-in或OpenRC conf.d被外部修改时，先保留并核对原件，不能用重新安装覆盖；恢复材料的三种区别见[MIGRATION](MIGRATION.md#安装卸载及附属服务的保留材料)。

## 手机SSH错行、无色和脚本输出

人类文本按真实终端列宽处理中文、长IPv6、域名和常见组合emoji，清理输入中的终端控制序列；不进入raw模式、不隐藏光标。NO_COLOR=1、TERM=dumb和非TTY均保留普通文本路径。字体仍可能影响emoji或模糊宽度字符，不宣称所有手机SSH应用已经验收。

```bash
NO_COLOR=1 TERM=dumb qingnode help
qingnode help --json
sudo qingnode list --json
sudo qingnode endpoint material --id NODE_ID --out /root/new-endpoint-check.json
```

机器JSON、客户端URI、配置文件和二维码不经过人类文本换行器。不要从屏幕折行文本拼回分享链接，改用显式export --out新的私有文件；二维码错位可改本地配置导入。取消表单不生成半个节点，应用中的进程中断与表单取消不同，仍保留恢复材料。输入文件及标准输入规则按各命令--help执行，不能把`--file -`当成所有命令的通用约定。

## 订阅可下载但代理失败

下载令牌只控制下载，代理UUID/密码才控制连接；撤销下载不能追回已下载的认证。先看`device show --id DEVICE_ID`及`subscription status`，核对实际绑定；共享凭据不能因停一个设备连带撤销其他设备。公网订阅还要验证HTTPS，本机回环服务通过不等于反向代理、公网入口或手机GUI通过。没有HTTPS先使用本地完整配置；没有可靠计量不显示虚构的已用0或硬配额成功。详见[订阅说明](SUBSCRIPTIONS.md)。
